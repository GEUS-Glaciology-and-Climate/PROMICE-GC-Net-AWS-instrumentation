# PROMICE-GC-Net-AWS-instrumentation

Centralizes information about the instrumentation at PROMICE and GC-Net automatic
weather stations (AWS) — currently scattered across ~20 years of fieldwork records in
inconsistent formats, folder structures, and naming conventions.

The near-term goal is to pull that information into one place per source type (starting
with maintenance sheets). The longer-term goal is a structured database that
[pypromice](https://github.com/GEUS-Glaciology-and-Climate/pypromice) — the processing
pipeline for PROMICE/GC-Net station data — can read directly, instead of instrumentation
history living only as scanned PDFs and Word docs on a network share.

## Contents

### Maintenance sheets

Station maintenance sheets record what was done to a station's instrumentation during a
field visit. Historically these live under `\\geodata\Ice\FIELDWORK\<year>\...`, one to
several files per station visit, in PDF, DOCX, or scanned-image form, with no consistent
naming or folder layout from year to year.

This repo pulls copies of those files out and renames them to a standard
`STATION_YEAR.ext` scheme (e.g. `DY2_2024.pdf`; `_2`, `_3`... suffixes when a station has
more than one sheet for the same year — repeat visits, multiple pages, instrument
variants, etc.):

- **`maintenance sheets/`** — the standardized copies. This is the actual deliverable.
- **`maintenance_sheets_classification.csv`** — the source-of-truth mapping, one row per
  candidate file found under FIELDWORK: original path, station code, year, and whether it
  was copied (`Copy`) or held back for manual review (`Skip-Ambiguous`, with a `Reason`).
  This file was built by hand, not by a pattern-matching script — the source data has too
  many one-off quirks (misspelled station codes, files covering several stations at once,
  folder names that don't match the station's official code, stations renamed over time)
  for automated matching to be reliable. Rows with `Status=Skip-Ambiguous` are cases that
  couldn't be confidently resolved and are worth a manual look; see each row's `Reason`.
- **`copy_maintenance_sheets.py`** — reads the classification CSV and performs the actual
  copy + sequential numbering + manifest generation. Deliberately "dumb": it has no
  matching logic of its own, it just executes the decisions already recorded in the CSV.
  Only reads from FIELDWORK (`shutil.copy2`); never writes, moves, or deletes anything
  there. Run it with `python copy_maintenance_sheets.py` after editing the classification
  CSV.
- **`maintenance_sheets_manifest.csv`** — generated by the script each time it runs:
  original path → copy filename actually produced, for every row (including skipped
  ones, so nothing found under FIELDWORK silently disappears from the record).

To fix a wrong station/year assignment or bring a flagged file back into scope, edit
`maintenance_sheets_classification.csv` and re-run the script.

## Roadmap

- Extend coverage beyond maintenance sheets to other instrumentation records (station
  configuration sheets, sensor swap/calibration logs, deployment/decommission dates,
  photos, etc.), following the same pattern: curated classification data + a small script
  to execute it.
- Consolidate everything into a proper database (schema TBD) that pypromice can query
  directly, replacing the current per-source CSV files.
